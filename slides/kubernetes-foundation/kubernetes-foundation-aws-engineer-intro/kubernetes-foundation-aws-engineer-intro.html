ECSで複雑化するとこんな壁にぶつかる

  • ALBリスナールールの肥大化：マイクロサービスが増えるたびにルールが積み重なり、100件制限に近づく
  • バッチ処理の複雑な組み合わせ：単発実行にEventBridge + Step Functions + Lambda が必要。ECSタスク単体ではリトライや完了確認が行えない
  • 環境差分管理の煩雑さ：ecspressoのJSONをdev/stg/prodで別々に管理すると変更のたびに3ファイルを修正する必要がある

KubernetesがECSの6つの弱点を解決する

  • Ingressで単一エントリーポイント：ALBは1つのまま。内部ルーティングはKubernetesが担い、チーム単位で独立管理できる
  • Job / CronJobでバッチをネイティブ管理：リトライ・完了確認・スケジューリングがマニフェスト1枚で完結。外部サービス不要
  • kustomizeで環境差分をパッチ管理：共通のbaseに対してenv差分だけをoverlayに記述。DRYな構成を保てる

ECS vs Kubernetes — 6つの観点で比較する

観点 ECS Kubernetes
ルーティング管理 ALBリスナールールがサービスごとに増殖。100件制限が現実的な課題になる Ingressで単一エントリーポイント。チーム単位でVirtualServiceを独立管理
バッチ処理 EventBridge + Step Functions + Lambdaを組み合わせる必要がある Job / CronJobリソースだけでリトライ・スケジューリング・完了確認が完結
環境差分管理 ecspressoのJSONを環境ごとに別ファイルで管理。変更箇所が分散する kustomizeのbase/overlayでDRYに管理。差分だけをパッチとして記述
デプロイ方式 Push型。明示的に更新を叩かないと反映されない Argo CDによるGitOpsでPull型。GitとクラスタをArgo CDが常に同期
ログ集約 サービスごとにCloudWatch Logsグループが分散。横断調査が困難 全PodのログがNodeに集約。Fluentdで任意の外部先に柔軟に転送可能

KubernetesはAWSを一段抽象化した存在

  • クラウドに依存しない共通語：KubernetesのマニフェストはAWSでもGCPでも同じ。裏でEC2やGCEが動いていてもKubernetesの操作は変わらない
  • AWSの知識が学習コストを削減：ECSタスク→Pod、ECSサービス→Deployment、ALB→Ingressと翻訳するだけで直感的に理解できる
  • 抽象化の分だけ機能が増える：SchedulerやControllerによる自動配置・自動復旧・自動スケーリングがネイティブに使える

マニフェストは3層構造で読める

# Deployment マニフェスト例 apiVersion: apps/v1 # ① APIグループ/バージョン kind: Deployment # ① 作りたいリソースの種類 metadata: name: slack-metrics-api # ② リソース名（一意） labels: app: slack-metrics # ② ラベル＝リソース間の接着剤 spec: replicas: 3 # ③ 起動するPod数 selector: matchLabels: app: slack-metrics # ③ このラベルのPodを管理 template: metadata: labels: app: slack-metrics spec: containers: - name: api image: myapp:1.0.0 # ③ 使うDockerイメージ ports: - containerPort: 8080
① kind / apiVersion
何を作るかを宣言。Deployment・Pod・Serviceなどリソース種別をここで指定する
② metadata
nameで一意に識別。labelsはリソース間のつながりを作る「接着剤」として機能する
③ spec
「どう動かすか」の仕様。replicasでPod数、imageでコンテナを指定する
ラベルが鍵
DeploymentのselectorとPodのlabelsが一致することでリソースが関連付けられる
