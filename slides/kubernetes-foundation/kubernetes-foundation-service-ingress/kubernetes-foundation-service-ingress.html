PodのIPが変わる問題をServiceが解決する

  • Podは使い捨て前提。再起動のたびにIPが変わるためクライアントは接続先を追えない
  • Service（ClusterIP）を置くと、固定の仮想IPと名前でPod群にアクセスできる
  • 複数Podが存在する場合はラウンドロビンで自動負荷分散。Podを入れ替えても接続先は変わらない
3 / 8

Serviceには4つのタイプがある

  • ClusterIP：クラスタ内専用の仮想IP。マイクロサービス間通信の標準
  • Headless（ClusterIP: None）：仮想IPなし。PodのIPをDNSで直接解決。StatefulSetのDB用
  • NodePort：ノードのポート（30000〜32767）を開けて外部公開。学習・暫定用
  • LoadBalancer：クラウドのLBを自動作成して外部公開。コストが高く管理が煩雑

5 / 8

IngressがL7でマイクロサービスを振り分ける

  • Ingress Controllerの実体はNginxのPod。NodePortで外部に口を開け、内部ではClusterIPへ転送する
  • Ingressリソースにホスト・パスのルールを定義。`/api → api-service`のようにL7で振り分ける
  • SSL終端もIngress Controllerが担う。各Podに証明書を配る必要がない

ローカル開発では/etc/hostsでDNSを手動設定。本番ではRoute 53などのDNSと組み合わせる

Service Type — 使い分け基準

タイプ 公開範囲 特徴 使用場面
ClusterIP クラスタ内のみ 仮想IP固定 / ラウンドロビン負荷分散 マイクロサービス間通信 / DBアクセス
Headless クラスタ内のみ 仮想IPなし / PodのIPをDNSで返す StatefulSetのDB / Pod個別アクセス
NodePort ノードIP経由で外部 ポート30000〜32767 / L4(TCP) ローカル検証 / 学習用
LoadBalancer クラウドLB経由で外部 クラウドLBを自動作成 / コスト高 小規模・単一Service公開
Ingress L7で外部（推奨） ホスト/パスルーティング / SSL終端 本番 / 複数マイクロサービス

NodePortは学習用・暫定。本番はIngress Controller（Nginx Pod）にL7ルーティングを集約する

IngressはL7の中央集権ルーター
